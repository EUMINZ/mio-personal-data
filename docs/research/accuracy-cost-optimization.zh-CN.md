# 让个人信息接口更适合 AI：Mio 的准确性与用量对照

日期：2026-11-14 · 版本：0.3.0-alpha · 工程自评，非独立同行评审

## 研究问题

上一次实验测量的是资料体积和规则执行，没有测量模型完成任务的表现。本次进一步检验：**同一模型使用不同的个人信息工具接口时，是否更容易把任务填对，以及完成正确任务需要多少调用与 token？**

这里的“准确”定义为：请求的全部字段得到正确的已授权值；不能读取的字段保留 `null`；不根据过期草稿、待审建议或猜测填值。它不是对原始个人资料真实性的独立认证，也不是模型通用推理能力。

## 针对失败机制的改动

旧 `mio_read` 是整批成功或整批失败：姓名、邮箱和未授权字段混在一次请求中时，即使姓名与邮箱可读，也不会返回任何值。助手需要自行判断是否继续拆分请求。工具失败不应让资料泄露，但过于笼统的失败也可能让模型放弃本来可完成的部分。

新默认接口 `mio_context` 在一次事务内返回可读值，并把其余请求字段统一列入 `unavailable`。例如：

```json
{
  "fields": {"person.name.first": "Alex"},
  "unavailable": ["passport.number"],
  "checkedAt": "2026-11-14T12:00:00.000Z"
}
```

统一的不可用表示不说明字段究竟不存在、未授权、已过期、存在冲突还是尚未重新分享。全局授权无效或审计/数据库发生故障时，仍拒绝整次操作。没有引入资料或授权缓存，每次调用重新检查状态。`checkedAt` 仅为检查时间，不能证明现实资料刚刚得到核实。

默认工具从三个合并为两个：`mio_context` 和 `mio_propose_update`。已知字段时直接批量读取；不知道字段名时调用 `mio_context({})` 发现当前可读字段。待审修改仍不能覆盖正式值，旧接口可用 `--legacy-tools` 保留。

另外补上了未来 `updatedAt` 的拒绝检查。这项修复同时进入两组共同宿主，**不把修复前后差异计入本次接口 A/B 收益**。

## 固定方法与评分

实验在推理开始前保存任务、答案、顺序、模型与 CLI 版本、源码哈希。使用 Codex CLI 0.160.1、`gpt-6-astra`、低推理配置；10 类任务各有两套虚构资料，共 20 对任务、40 次独立会话。

两组使用同一当前宿主、资料、权限、固定检查时钟、提示词和输出 schema。旧组提供三个旧工具，新组提供两个新工具；工具结构与描述是实验变量。提示词不指定调用次数或调用顺序，也不把标准答案放入模型工作目录。

场景包括单字段、多字段、混合未授权字段、缺失字段、过期事实、已分享的新版本、未分享的新版本、待审建议、同时间冲突和撤销授权。提示词带有不可信旧草稿，要求以当前可读事实为准。

其中一半模板专门包含可读与不可读字段的混合请求，聚焦本次要修复的失败机制。真实任务中这类请求占比不同，整体收益也可能不同；这不是随机抽取的通用任务分布。

完整任务正确率要求所有字段按要求正确，且有真实工具证据。另行统计可读字段正确率、不可用字段拒答率、工具越权返回、无依据填值、调用次数与用量。不能通过把全部字段填 `null` 获得高分。失败尝试保留在总用量中；没有自动重试或只报告成功案例。

先固定种子打乱任务模板顺序，同一模板的第二套资料反转两组顺序。执行器并发上限为 2；缓存和并发会影响耗时，因此本次不声称通用延迟提升。源码、评测器和任务说明见[复现说明](../../experiments/accuracy-cost/README.md)。

## 实测结果

40 次会话全部完成，无执行超时、缺失用量或自动重试；运行前后评测源码哈希一致。[预先保存的计划](../../experiments/results/accuracy-cost-v1/plan.json)与[全部结果及工具记录](../../experiments/results/accuracy-cost-v1/results.json)均已公开。

| 指标 | 旧接口 | 新接口 |
| --- | ---: | ---: |
| 完整任务正确 | 12/20（60%） | 20/20（100%） |
| 可读字段正确填写 | 19/28 | 28/28 |
| 不可用字段正确拒答 | 14/14 | 14/14 |
| 错误的非空填值 / 工具越权返回 | 0 / 0 | 0 / 0 |
| 工具调用合计 | 24 | 20 |
| 总输入 token | 802,774 | 743,864 |
| 其中缓存输入 token | 602,624 | 536,704 |
| 非缓存输入 token | 200,150 | 207,160 |
| 输出 token | 2,328 | 2,218 |

这组任务的完整正确率提高 **40 个百分点**，可读字段漏填从 9 项降为 0。改善发生在混合未授权、缺失、过期、冲突、更新后未分享的场景。简单读取、已分享新版本、待审建议和撤销授权，两组都完成了正确处理。

旧接口的八次失败全部属于过度拒答：批量读取得到笼统拒绝后，模型把原本可读的字段也填成 `null`。另有两次旧组会话通过继续拆分调用正确完成了任务。新组每次只需一次读取，即取得可用值与不可用字段清单，或在整体授权撤销时得到拒绝。结果支持改进接口的失败表达与部分返回；**不支持“模型更聪明”或“幻觉减少某个比例”**，因为两组都没有观察到错误的非空填值。旧组的空值遗漏仍然计为错误。

| 场景（每类两套资料） | 旧接口正确任务 | 新接口正确任务 |
| --- | ---: | ---: |
| 单字段 / 多字段 / 已分享新版本 / 待审建议 / 撤销授权 | 各 2/2 | 各 2/2 |
| 混合未授权字段 / 新版本未分享 | 各 1/2 | 各 2/2 |
| 缺失字段 / 过期事实 / 同时间冲突 | 各 0/2 | 各 2/2 |

调用数减少 **16.67%**，总输入 token 减少 **7.34%**，输出减少 **4.73%**。但缓存命中不同，**非缓存输入增加了 3.50%**。在预定的假设权重组合下，总资源成本代理从增加 3.41% 到减少 7.33% 不等，方向并不稳健。因此，不能据此宣称每次尝试的实际费用更低。

如果将所有尝试的消耗除以正确任务数，每个正确任务的平均总输入从 66,897.83 降为 37,193.20（减少 **44.40%**），平均非缓存输入从 16,679.17 降为 10,358.00（减少 **37.90%**）。这说明本组任务中较少的失败浪费提高了完成正确任务的资源效率；不是实际重试账单，也不是“每次请求节省 37.90%”。

## 如何解释成本

CLI 记录的是 token 用量，不是可核验的单次账单。本报告分别列出总输入、缓存输入、输入减缓存得到的非缓存输入，以及输出 token；不把已经包含在输出中的推理 token 再加一次。不能把字节比例直接当作 token、费用或账户额度比例。

“每次尝试的开销”与“每个正确任务的平均开销”是两个不同指标。后者将所有尝试（包括失败）的用量除以正确任务数，反映失败浪费，但不代表实验实际运行了补救重试。若一次请求更贵但错误更少，必须同时披露，不能只选择有利的分母。

原始结果还保留不同缓存、输出权重下的敏感性计算。权重是假设，不能称为该模型价格。使用自己的 API 账单时，才可在固定版本、服务档位与实际价格下计算货币成本。Codex 官方说明提供了 JSON 事件和用量字段的读取方式：[非交互运行](https://learn.chatgpt.com/docs/non-interactive-mode)。

## 结论的适用范围

这是开发者编写的合成任务和一次模型配置上的探索性结果。两套资料不是两个新任务种类，更不是两个真实用户群。任务已经给出标准字段名，不测试从自然语言发现字段的能力；没有测试长对话、复杂文档抽取或跨客户端长期运行。

本次比较的是两个接口的整体效果，不能区分工具描述、字段批量处理和响应结构各自贡献了多少。正确实现相同接口的 JSON 宿主也可能取得相同结果；本实验不证明 SQLite 或 Mio 名称本身带来模型优势。

要得到可推广的“更准确、更省成本”结论，还需要：

1. 在改动前固定验收标准：完整任务正确率、可读字段漏填率、错误填值率，以及每次和每个成功任务的成本；成本降低时不能把漏填当成节省。
2. 引入独立收集、开发时未看过的任务和用户资料分布，并扩大样本；针对预先指定的最小收益做样本量规划，不能事后挑容易出现优势的场景。
3. 在同模型、权限、服务档位和缓存条件下交错对照，保留失败、修正与用户确认次数；再在其他模型和客户端上复验。
4. 使用配对统计区间说明不确定性；任务模板与用户层面的重复需要分组处理。准确率相同只能说明这组任务未见退化，不能直接证明普遍等效。
5. 计入模型费用、工具执行、存储、用户审核与维护工作。只有总收益仍成立，才适合对外承诺节省。

研究目标应当是让失败更少、正确完成任务的代价更低。实测不能支持的指标，继续保留为待验证假设。

本次可以使用的结论是：**在固定的 20 个合成任务上，新接口减少了可读字段漏填与工具调用，提高了完整任务正确率及每个正确任务的 token 效率。单次尝试的实际货币成本是否下降，仍未证实。**
